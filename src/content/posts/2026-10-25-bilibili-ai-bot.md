起因很朴素：我在 B站 有个小号，平时没人管。我想给它接个 AI——评论区有人 @ 它，它能自己接话；闲着的时候去首页捞点好玩的视频，每天喂给我十条。

东西做完了，代码在 [yexuan722/feiyu-bot](https://github.com/yexuan722/feiyu-bot)。但真正值得写的是后半段：**功能三天写完，剩下三天全在修四个字段。**

这篇按「现象 → 怎么查出来的 → 怎么修」记录，每个坑都给结论，不铺过程。

---

## 零、先说清楚：这东西合不合规

不合规。

B站 没给个人号开 bot 接口。所有「AI 号」本质都是拿 Cookie 调网页端自用的内部接口，违反《用户协议》；一旦被风控，轻则评论只有自己可见，重则限流封号。

所以我的默认配置是**最保守那一档**：

- 生成全自动，**发送要人点一下**（本地网页上的按钮）
- 全自动可开，但硬限速：6 条/小时、30 条/天、最小间隔 60 秒
- **不做「在评论区 @ 主号」**。那属于引流，是最容易被举报、最容易连坐的一条，我直接不写。

后面所有工程决策，都是围着「别把号玩死」转的。

## 一、整体长什么样

两条链 + 一个本地面板。

| 模块 | 干什么 |
|---|---|
| 互动链 | 拉「@我的 / 回复我的」→ 去重 → 喂给模型 → 进待发队列 → 人工确认或自动发 |
| 发现链 | 热门 + 首页推荐 → 去重过滤 → 模型打分 → 按口味加权 → 每天挑 10 条 |
| 驾驶舱 | 本地 HTTP 服务，一个页面：审核队列、投喂卡片、tag 权重、日志 |

几个刻意的选择：

- **纯标准库**，零第三方依赖。`urllib` + `sqlite3` 够用了，装依赖是给未来的自己挖坑。
- **SQLite 存三样东西**：待发队列、已投喂、去重游标。删了 `data/` 就等于失忆。
- **人设单独一个 Markdown**（`bbot/persona.md`）。调语气不用碰代码，这点比什么提示词工程都管用。

## 二、坑一：回复跑到了视频底下

**现象**：别人 @ 小号，AI 回了，但那条回复是视频评论区的一条**新顶层评论**，看起来像在自言自语。

**怎么查的**：把接口返回的原始 JSON 落盘。一条 @ 消息长这样：

```json
"item": {
  "subject_id": 117439320818637,   // 视频 aid
  "root_id": 0,
  "target_id": 0,
  "source_id": 321809427136,       // ← 被 @ 的那条评论 rpid 在这里
  "native_uri": "bilibili://video/...&comment_root_id=321809427136"
}
```

**根因**：我按直觉认了 `root_id` / `target_id`，两个都是 0。发评论的接口拿到 `parent=0`，就把这条当成新的顶层评论处理了。

而 `source_id` 才是那条评论的 rpid——字段名和语义完全对不上。

**修法**：

```python
parent = target_id or source_id
root   = root_id or url 里的 comment_root_id or source_id
```

顺手加了两道保险：

1. 只有 `root` 没有 `parent` 时，去那条评论的子回复里按「谁 + 说了什么」找具体那一层；找不到就退回顶层评论。
2. 两个都没有时**直接拒绝发送**，报错说明「会变成视频下的新评论」。想强行发，得手动开 `allow_top_level_reply`。

**结论**：B站 的 `root_id`/`target_id` 是「回复某条回复」时才填的，普通 @ 场景全是 0。别信字段名，信实测。

## 三、坑二：私信根本发不出去

**现象**：会话列表能拉到 10 个，但一拉消息就 `HTTP 404`。

查公开的 API 收集文档，发现三处全错：

| 我原来的做法 | 实际 |
|---|---|
| `svr_sync/v1/svr-sync/msgfeed` | 早就废弃，改成 `svr_sync/v1/svr_sync/fetch_session_msgs` |
| 发私信只发 form 表单 | URL 上必须带 WBI 签名参数 `w_sender_uid` / `w_receiver_id` / `w_dev_id` / `w_rid` / `wts`，**正文里再带一份** `msg[...]`，两边缺一不可 |
| `dev_id` 从 `buvid3` 的 md5 派生 | 就是个 **UUID v4**，跟设备指纹毫无关系 |

第三条尤其坑——我按「从 buvid3 派生」这个思路写了两种拼法轮着试，全是错的。文档里一句 `dev_id 实质上就是 UUID（版本 4）` 就解决了。

**怎么验证的**（不想真的骚扰别人）：给**自己**发一条。接口返回：

```
21026 不能给自己发送消息哦~
```

这个错误码不是失败，是**成功的证据**：鉴权、签名、参数全部通过，只是被一条业务规则拦下了。签名错的话这里会是 `-400`。

**结论**：报错码能区分「你参数错了」和「你参数对了但业务不让」。用错误码做验收，比看文档靠谱。

顺带记住几个业务限制：`21047` 对方没关注你没回复你之前只能发 1 条；`21020/21046` 发太快；`25003` 对方隐私设置。

## 四、坑三：有些视频抓不到 tag

**现象**：投喂列表里，一部分视频有 tag，一部分没有。

**怎么查的**：把没 tag 的都拎出来，打印 aid——

```
[9] 史上首款2nm芯片…  aid=0  tags=[]
[8] 来屎山之巅…        aid=0  tags=[]
[8] 这家最懂AI安全的公司  aid=0  tags=[]
```

`aid=0`。而 `_fill_tags` 里第一行就是 `if not aid: continue`，**静默跳过，连日志都不打**。

**根因**：从「热门」来的视频，接口字段叫 `aid`；从「首页推荐流」来的，视频号塞在 `id` 里，压根没有 `aid` 字段。我只解析了前者。

**修法**：

1. `aid` 为空且 `id` 是数字 → 直接拿来当 aid；连 bvid 都没有 → 用 `view(aid)` 反查。
2. tag 查询支持只给 bvid：先 `view` 换出 aid 再打 tag 接口。
3. **失败必须打日志**。现在会区分两种：`! 取 tag 失败 BVxxx: [code]`（真失败）和 `· BVxxx 这个视频没有 tag`（UP 主没设）。

还加了条补数据命令 `tags --fix`，把存量 38 条一次性补回来了。

**结论**：静默失败是最坏的失败。能不写 `continue` 就不写，要写就带日志。

## 五、坑四：私信扫到了，就是不回

**现象**：私信自动回复开了，日志里也在「扫一遍私信」，但对方发来的消息就是没回。

**怎么查的**：复现判定逻辑，逐个会话打印为什么跳过：

```
会话 160403515：unread=0
[对方] 19:00  晚上好，吃了吗？   source=2
[对方] 19:02  吃了吗            source=2

跳过的原因：unread=0，被第一条规则跳过了
```

**根因**：我拿 `unread_count > 0` 当「有新消息」的判据。但这是**给人看的字段**——你在网页或手机上点开那个会话看一眼，未读数立刻归零，而消息其实还没回。

客户端的一次「看一眼」，就把 bot 的判断依据抹掉了。

**修法**：换成**会话时间游标**。`meta` 表里给每个会话存上次扫到的时间戳，只有会话时间往后走了才重新拉消息。

```python
last_scan = float(store.get_meta(f"dm_ts_{talker}", "0") or 0)
if session_ts <= last_scan:
    continue
```

顺带做了两件事：

- 跳过系统消息（互相关注提示、活动通知、自动回复），只认 `msg_source` 在 `{0,1,2,3,4,7}` 的真人消息——不然第一版对着「我们已互相关注，开始聊天吧~」回了半天。
- 加了 `dm --explain`，逐会话打印「只有系统消息，跳过」「最后一句是我发的，跳过」「已经生成过草稿，跳过」。

**结论**：`unread_count` 是「你还没读」，不是「还没回」。前端字段的含义要对齐使用场景，不然逻辑对、数据对、结果错。

## 六、几个设计上的取舍

**推荐不要做成纯 top-N。** 每天固定 10 条，但排序是

```
最终分 = 模型分 + tag 加分 + 随机抖动(±1.2)
tag 加分 = Σ(tag 权重 × 0.5)，且总和封顶 ±1.5
```

三层限制是故意的：单个 tag 权重限幅在 `[-3, 3]`，加分封顶 1.5 分，再加随机抖动。点十次「美食」也不会把首页刷成美食频道——**给用户影响权重，但不给支配权**。

**模式切换要能立刻生效。** 配置在内存里，面板点一下就改内存 + 落盘，不用重启进程。命令行 `mode --auto` 是先打本地 API，打不通才退回到改配置文件。

**常驻不要用计划任务。** 「登录时启动」的 schtasks 任务需要管理员权限，普通用户直接被拒。改成写 `HKCU\...\Run`，配 `pythonw.exe`（无窗口），不需要提权。

**Cookie 会过期。** `SESSDATA` 的明文是 `随机串,过期时间戳,签名`，第二个字段直接解析出来，面板上显示「剩 179 天」，少于 14 天变黄。

## 七、两个非技术坑

**① 别用 PowerShell 改中文源码。**

我图快，用 `Get-Content | -replace | Set-Content` 批量把 `print(` 换成 `log(`。PowerShell 5.1 默认按 ANSI 读写，整个文件的中文注释变成一坨 `锛?`，文件直接废了。只能整篇重写。

教训：**文本编辑交给编辑器/工具，别交给 shell 管道。**

**② API Key 别贴错栏。**

交互式配置里，`base_url` 那一栏是要网址的。我把 key 粘进去了，还截图发出去问问题——相当于公开了凭证。

处理：立刻吊销重建。代码里也加了兜底——**输入以 `sk-` 开头就自动识别成 key，挪到该去的字段**，并提示一句。

教训：给人类设计的输入框，默认人类会填错。

## 八、花了多少钱

用 `deepseek-flash`，按官方价估算：

| 项目 | 单次 | 一天最多 |
|---|---|---|
| 一条回复（~1000 输入 + 50 输出 token） | ~0.003 元 | 30 条 ≈ 0.1 元 |
| 一轮视频打分（15 条一批） | ~0.005 元 | 首次约 6 轮 ≈ 0.03 元 |
| 合计 | | **0.2～1 元/天** |

日常跑下来比这更省——大部分时间在「没有新面孔」的空转。真正贵的是**开启思考模式**：DeepSeek 默认开思考，写 40 字评论前先想半天，输出 token 翻几倍。所以请求体里固定带了 `{"thinking": {"type": "disabled"}}`。

## 收尾

做完之后我的结论是：**难的不是「接上 AI」。**

接模型、写提示词、搭个本地页面，都是熟活。真正花时间的是那些**文档里没写、只对真人成立的前端假设**：

- `root_id` 在普通 @ 场景是 0，真正的是 `source_id`
- 推荐流的视频号在 `id` 里，不在 `aid` 里
- `dev_id` 看着像设备指纹，其实是个随机 UUID
- `unread_count` 是「未读」，不是「未回」

这些东西的共同点：**你按字段名猜，一定猜错；你把真实响应落盘看一眼，五分钟就懂了。**

所以整篇最值钱的一条建议是：**先 dump，再写代码。**

代码在 [feiyu-bot](https://github.com/yexuan722/feiyu-bot)，跑起来要自己粘 Cookie 和换一个 API Key，仓库里没有我的任何凭证。
